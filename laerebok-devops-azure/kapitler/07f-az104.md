## 7.6 AZ-104: Microsoft Azure Administrator

### Om sertifiseringen

**Hva er det?** AZ-104 gir tittelen **Microsoft Certified: Azure Administrator Associate**. Den tester at du kan **implementere, administrere og overvåke** et Azure-miljø: identiteter, styring, lagring, compute, nettverk og overvåking. Den er betydelig mer praktisk og krevende enn AZ-900.

**Hvorfor ta den?** Den er en av de mest etterspurte Azure-sertifiseringene for drift-, sky- og DevOps-roller, og grunnlaget for videre sertifiseringer som *AZ-400 (DevOps Engineer Expert)* og *AZ-305 (Solutions Architect Expert)*.

**Praktisk informasjon** (verifiser på Microsoft Learn, «Microsoft Certified: Azure Administrator Associate», og les den nyeste *study guide* – pensum oppdateres jevnlig):

| | |
|---|---|
| Nivå | Associate |
| Format | Flervalg, case-studier, dra-og-slipp, «ja/nei»-serier; kan inneholde interaktive oppgaver |
| Tid | Omtrent 100 minutter for selve eksamen |
| Bestått | 700 av 1000 poeng |
| Gyldighet | 1 år; fornyes gratis med en online fornyelsestest på Microsoft Learn |
| Hjelpemidler | Under eksamen har Associate-eksamener tilgang til Microsoft Learn (åpen bok i begrenset form) – sjekk gjeldende regler |
| Forkunnskaper | Anbefalt minst 6 måneders praktisk Azure-erfaring – lab-arbeid i denne boken hjelper |

### Sertifiseringsmål (domener)

Vektingen ved siste revisjon var omtrent slik:

| Domene | Vekt (ca.) | Kapitler |
|---|---|---|
| **Manage Azure identities and governance** | 20–25 % | 7.1 |
| **Implement and manage storage** | 15–20 % | 7.3 |
| **Deploy and manage Azure compute resources** | 20–25 % | 7.2, 7.4, 9, 10 |
| **Implement and manage virtual networking** | 15–20 % | 2, 7.2 |
| **Monitor and maintain Azure resources** | 10–15 % | 7.3, 13 |

**Viktige ferdigheter per domene:**

1. **Identiteter og styring:** brukere og grupper (også masseopprettelse og gjester), lisenser, SSPR; RBAC-roller og tildelinger på riktig scope, tolke tilganger; Azure Policy; låser; tags; ressursgrupper, abonnementer og management groups; budsjetter, kostnadsvarsler, Advisor.
2. **Lagring:** brannmur og virtuelle nettverk på lagringskontoer, SAS (konto, tjeneste, user delegation) og *stored access policies*, tilgangsnøkler og rotasjon, identitetsbasert tilgang til Azure Files; redundans, objektreplikering, kryptering (inkl. kundeadministrerte nøkler); containere, nivåer, soft delete, snapshots, versjonering, livssyklus; AzCopy og Storage Explorer.
3. **Compute:** tolke og endre ARM-maler og Bicep-filer, eksportere maler; opprette og administrere VM-er (størrelser, disker, kryptering, flytte VM-er mellom grupper/abonnementer/regioner, availability sets og soner, VM Scale Sets); containere (ACR, Container Instances, Container Apps, størrelser og skalering); App Service (planer, skalering, TLS-sertifikater, egne domener, backup, nettverk, deployment slots).
4. **Nettverk:** VNets og subnett, peering, offentlige IP-adresser, brukerdefinerte ruter (UDR), feilsøking av tilkobling; NSG og ASG, effektive regler, Azure Bastion, service endpoints og private endpoints; Azure DNS; interne og offentlige lastbalanserere og feilsøking av dem.
5. **Overvåking og vedlikehold:** metrikker, logger, varsler, action groups, *alert processing rules*, Log Analytics-spørringer, VM/storage/network insights, Network Watcher og Connection Monitor; Recovery Services vault og Backup vault, backup-policyer, gjenoppretting, Azure Site Recovery, backup-rapporter og -varsler.

### Laboppgaver

Alle labbene bruker ressursgrupper som starter med `rg-az104-`. **Slett dem etter hver lab.**

**Lab 1 – Identitet og RBAC.**
1. Opprett gruppene `helpdesk` og `nettverksteam` og to testbrukere.
2. Gi `helpdesk` rollen *Virtual Machine Contributor* på `rg-az104-lab1`.
3. Logg inn som testbrukeren (privat vindu). Bekreft at brukeren kan starte/stoppe VM-er, men ikke endre VNet.
4. Bruk *Access control (IAM) → Check access* for å se effektive tilganger.

**Lab 2 – Styring.**
1. Lag management group `mg-az104` og flytt abonnementet inn (hvis du har rettigheter – ellers gjør resten på abonnements- eller ressursgruppenivå).
2. Tildel «Require a tag on resource groups» (tag `kostnadssted`) med effekt Deny.
3. Prøv å opprette en ressursgruppe uten tag (feiler) og med tag (virker).
4. Tildel «Inherit a tag from the resource group if missing», lag en ressurs, og kjør en *remediation task*.
5. Legg en `CanNotDelete`-lås på gruppen og prøv å slette den.

**Lab 3 – Lagring.**
1. Lag en StorageV2-konto med ZRS. Slå av offentlig blob-tilgang og nøkkelbasert tilgang.
2. Lag en container, last opp filer med Entra-innlogging.
3. Lag en *stored access policy* på containeren og en tjeneste-SAS som refererer til den. Opphev tilgangen ved å slette policyen.
4. Slå på soft delete og versjonering, slett en blob og gjenopprett den.
5. Lag en livssyklusregel som flytter blobs til Cool etter 30 dager.
6. Lag en filshare og monter den fra en Azure-VM.

**Lab 4 – VM-er.**
1. Deploy to VM-er i forskjellige soner med en Bicep-fil (fra kapittel 7.4 som utgangspunkt).
2. Legg til en datadisk, partisjoner, formater og monter den i Linux (`lsblk`, `sudo mkfs.ext4`, `/etc/fstab` med UUID).
3. Endre størrelsen på en VM. Hva skjer med VM-en under endringen?
4. Lag en VM Scale Set med autoskalering basert på CPU (min 1, maks 3).
5. Eksporter en mal fra ressursgruppen (*Export template*) og les den.

**Lab 5 – App Service og containere.**
1. Lag en App Service Plan (S1 eller høyere for slots), en web-app, og en `staging`-slot.
2. Deploy versjon 1 til produksjon og versjon 2 til staging. Gjør en swap.
3. Konfigurer autoskalering for planen.
4. Bygg et image, push til ACR, og kjør det i Azure Container Instances (`az container create`) og i Container Apps (`az containerapp up`).

**Lab 6 – Nettverk.**
1. Lag `vnet-hub` (10.0.0.0/16) og `vnet-spoke` (10.1.0.0/16) og peer dem (begge veier).
2. Lag én VM i hver uten offentlig IP. Bruk Bastion og test `ping`/`curl` mellom dem.
3. Lag en NSG som bare tillater SSH fra hub til spoke. Verifiser med *IP flow verify*.
4. Lag en route table med en UDR som sender `0.0.0.0/0` til en *virtual appliance*-IP og se på *Effective routes*.
5. Lag en privat DNS-sone med automatisk registrering, og slå opp VM-navn fra den andre VM-en.
6. Lag en lagringskonto med Private Endpoint og verifiser at `nslookup <konto>.blob.core.windows.net` gir privat IP fra VM-en.

**Lab 7 – Lastbalansering og feilsøking.**
1. Sett to webservere bak en Standard Load Balancer med helsesjekk.
2. Stopp nginx på én – observer *backend health* og trafikkfordelingen.
3. Bruk *Network Watcher → Connection troubleshoot / Connection Monitor* mellom en VM og en ekstern adresse.

**Lab 8 – Overvåking og backup.**
1. Lag et Log Analytics workspace og send VM-logger dit med Azure Monitor Agent og en Data Collection Rule.
2. Lag et CPU-varsel med en action group. Utløs det med `stress-ng`.
3. Skriv en KQL-spørring som viser *Heartbeat* per VM siste time.
4. Ta backup av en VM, og gjenopprett én fil med *File recovery*.

### Eksamenstips

- **Les spørsmålet nøye.** Ord som «minimize administrative effort», «least privilege» og «minimize cost» avgjør hvilket av flere *mulige* svar som er *riktig*.
- **Kjenn grensene:** 5 reserverte IP-er per subnett, NSG-prioritet 100–4096 (lavest først), peering er ikke transitiv, lagringskontonavn 3–24 små bokstaver/tall.
- **Kjenn forskjellene:** availability set vs. zone, LRS/ZRS/GRS/GZRS, Load Balancer vs. Application Gateway, service endpoint vs. private endpoint, Recovery Services vault vs. Backup vault, Entra-roller vs. Azure-roller.
- **Ja/nei-serier:** Samme scenario med ulike løsningsforslag – vurder hvert forslag isolert. Du kan ikke gå tilbake til disse.
- **Bruk tiden:** Case-studier tar tid. Marker vanskelige spørsmål og kom tilbake.

### Prøveeksamen AZ-104 (30 spørsmål)

Sett av 60 minutter.

1. Du må gi en gruppe tilgang til å administrere VM-er i én ressursgruppe, men ikke nettverket eller lagringen. Hvilken rolle og hvilket scope?
2. En bruker har *Owner* på et abonnement. En ressursgruppe har en `ReadOnly`-lås. Kan brukeren legge til en tag på en VM i gruppen?
3. Du må sikre at alle nye ressurser har taggen `kostnadssted`, og at ressurser uten taggen **ikke kan opprettes**. Hva bruker du?
4. Ressursgruppen har taggen `prosjekt=x`. Får en ny VM i gruppen automatisk samme tag?
5. Du skal gi en ekstern partner lesetilgang til én blob i 24 timer uten å opprette en konto for dem. Hva er den sikreste metoden?
6. Du har utstedt flere SAS-tokens basert på en *stored access policy*. Hvordan opphever du alle samtidig?
7. En lagringskonto må tåle at en hel tilgjengelighetssone feiler, og data skal ikke forlate regionen. Hvilken redundans?
8. Data som sjelden leses, skal lagres billigst mulig, men må kunne leses innen millisekunder når det trengs. Hvilket nivå?
9. Du skal kopiere 5 TB fra en lokal server til Blob Storage over nettverket med et skriptbart kommandolinjeverktøy. Hvilket?
10. Du har en VM i et availability set. Hva beskytter dette mot?
11. Du må endre størrelsen på en VM til en størrelse som ikke er tilgjengelig i den nåværende maskinvareklyngen. Hva må du ofte gjøre først?
12. En VM viser *Stopped* i portalen etter at noen kjørte `shutdown` i OS-et. Betaler dere for compute?
13. Du vil at antall VM-instanser skal øke automatisk når gjennomsnittlig CPU er over 70 %. Hvilken tjeneste?
14. Du skal teste en ny versjon av en web-app i produksjonsmiljøet og bytte uten nedetid. Hvilken App Service-funksjon, og hvilket minste nivå kreves?
15. En app i App Service må nå en database i et VNet via privat IP. Hva konfigurerer du på App Service?
16. Hvilken tjeneste kjører en enkelt container raskest, uten orkestrering, med fakturering per sekund?
17. Du har VNet A (10.0.0.0/16) og VNet B (10.0.0.0/16). Kan du peere dem?
18. VNet A er peeret med B, og B er peeret med C. Kan A og C kommunisere direkte?
19. Hvor mange IP-adresser kan du bruke til VM-er i et subnett `10.1.5.0/28`?
20. En NSG på subnettet tillater port 443. En NSG på VM-ens NIC har ingen egendefinerte regler. Når trafikk på 443 fra internett frem til VM-en?
21. Du vil la en VM nå en lagringskonto via en privat IP i VNet-et, og blokkere offentlig tilgang til kontoen. Hva bruker du?
22. Hva er forskjellen på en service endpoint og en private endpoint?
23. Du må tvinge all utgående internettrafikk fra et subnett gjennom en brannmur-VM. Hva lager du?
24. Du trenger SSH-tilgang til VM-er uten offentlige IP-er og uten VPN. Hvilken tjeneste?
25. Du skal fordele HTTPS-trafikk basert på URL-sti og beskytte mot SQL-injeksjon. Hvilken tjeneste?
26. Helsesjekken til en Load Balancer feiler for alle VM-er, men nginx kjører. NSG-en har en regel *DenyAll* inn på prioritet 100. Hva er sannsynlig årsak?
27. Du vil analysere hvilke regler som tillot eller blokkerte en bestemt pakke til en VM. Hvilket verktøy?
28. Du skal få e-post og SMS når en VM har vært utilgjengelig i 5 minutter. Hvilke to komponenter i Azure Monitor trenger du?
29. Hvilket hvelv bruker du for å ta backup av Azure VM-er og Azure Files?
30. Du må kunne gjenopprette en hel applikasjon (flere VM-er) i en annen region med RPO på minutter. Backup eller Site Recovery?

### Fasit med forklaringer

1. **Virtual Machine Contributor** på **ressursgruppen**. Minste privilegium: bare VM-er, bare der.
2. **Nei.** Låser gjelder alle brukere, også Owner. ReadOnly hindrer endringer (som tags). Fjern låsen først (hvis du har rettighet).
3. **Azure Policy** med effekt **Deny** (f.eks. «Require a tag and its value on resources»).
4. **Nei.** Tags arves ikke automatisk. Bruk Policy (*Inherit a tag from the resource group*) med Modify-effekt.
5. **User delegation SAS** (signert med Entra-legitimasjon) med kun lese-rettighet og 24 timers utløp. Den er sikrere enn en SAS signert med kontonøkkel.
6. **Endre eller slett den lagrede tilgangspolicyen** (*stored access policy*). Alternativt rotere kontonøkkelen som signerte dem – men det påvirker alt annet som bruker nøkkelen.
7. **ZRS.** (GRS/GZRS sender kopier til en annen region.)
8. **Cool** eller **Cold** (avhengig av hvor sjelden og minimum lagringstid). **Ikke Archive** – der må data rehydreres i timer.
9. **AzCopy.**
10. Maskinvare-/rack-feil (fault domains) og planlagt vedlikehold (update domains) **innenfor ett datasenter** – ikke tap av hele datasenteret.
11. **Deallokere (stoppe)** VM-en, slik at den kan flyttes til maskinvare som støtter størrelsen.
12. **Ja.** Den er ikke deallokert. Stopp/dealloker fra portalen eller med `az vm deallocate`.
13. **Virtual Machine Scale Sets** med autoskaleringsregel.
14. **Deployment slots** med **swap**. Krever **Standard** eller høyere.
15. **VNet integration** (regional), eventuelt sammen med en Private Endpoint og privat DNS for databasen.
16. **Azure Container Instances.**
17. **Nei.** Adresseområdene overlapper.
18. **Nei.** Peering er ikke transitiv. Peer A–C direkte, eller bruk hub-and-spoke med ruting gjennom en NVA/Azure Firewall eller Virtual WAN.
19. **11.** /28 gir 16 adresser, minus 5 reservert av Azure.
20. **Nei.** Når det finnes NSG både på subnett og NIC, må **begge** tillate trafikken. En NSG uten egendefinerte regler har bare standardreglene, og *DenyAllInBound* blokkerer trafikk fra internett. (Hadde NIC-en **ingen** NSG i det hele tatt, ville trafikken sluppet frem.) Dette er en klassisk eksamensfelle: les nøye om NIC-en har «en NSG uten regler» eller «ingen NSG».
21. **Private endpoint** for lagringskontoen, privat DNS-sone (`privatelink.blob.core.windows.net`), og *Public network access: Disabled*.
22. **Service endpoint**: trafikken fra subnettet går over Microsofts nett til tjenestens **offentlige** endepunkt, og tjenesten kan begrenses til subnettet. **Private endpoint**: tjenesten får en **privat IP** i VNet-et ditt; kan også nås fra peerede nett og lokalt via VPN/ExpressRoute.
23. En **route table** med en **UDR** `0.0.0.0/0 → Virtual appliance (brannmurens private IP)`, knyttet til subnettet.
24. **Azure Bastion.**
25. **Application Gateway med WAF** (eller Front Door med WAF for globale scenarier).
26. NSG-regelen på prioritet 100 **blokkerer helsesjekkene** fra `AzureLoadBalancer` (de tillates normalt av standardregelen på 65001, men en egendefinert DenyAll med lavere tall vinner). Legg til en regel som tillater service tag `AzureLoadBalancer` med lavere prioritetstall enn 100 – eller endre DenyAll-regelen.
27. **Network Watcher → IP flow verify** (og *Effective security rules*).
28. En **alert rule** (f.eks. metrikk *VM Availability* eller en log alert på Heartbeat) og en **action group** (e-post og SMS).
29. **Recovery Services vault.**
30. **Azure Site Recovery** – kontinuerlig replikering gir RPO på minutter og orkestrert failover til en annen region.

**Vurdering:** 24+ riktige: god form. 18–23: repeter domenene der du bommet og gjør labbene på nytt. Under 18: gå gjennom kapittel 7.1–7.3 og labbene systematisk før du prøver igjen.
